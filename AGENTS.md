# Codoxear architecture notes

This repo is a Linux-first companion UI for continuing local CLI agent sessions on a phone/laptop browser.

Currently supported agent backends:

- `codex`
- `pi`
- `cc` (Claude Code; launches `claude`)

## Components

### `codoxear.server`

- HTTP server (single process) that serves the UI and a small JSON API under `/api/*`.
- Auth: password gate using `CODEX_WEB_PASSWORD` (required). Cookie-based session (`codoxear_auth`).
- Session discovery: scans `~/.local/share/codoxear/socks/*.sock` for broker control sockets and reads the adjacent `*.json` metadata.
- Web-owned sessions: `/api/sessions` (POST) spawns a new broker process with `CODEX_WEB_OWNER=web` and a chosen `agent_backend`.
- Terminal-owned sessions: created by running `codoxear-broker` with the desired backend environment (for example plain Codex broker wrappers, `CODEX_WEB_AGENT_BACKEND=pi` for Pi, or `CODEX_WEB_AGENT_BACKEND=cc` for Claude Code).
- `GET /api/sessions` returns backend-aware launch defaults, including provider/model/reasoning choices per backend.
- Runtime state directory: `~/.local/share/codoxear` (legacy `~/.local/share/codex-web` is no longer used).
- Additional persisted UI state includes `session_sidebar.json`, `session_files.json`, `session_queues.json`, `unattended.json`, and `session_aliases.json` under the same app dir.

### `codoxear.broker`

- Foreground PTY wrapper intended to be run from a real terminal.
- Starts the selected backend CLI (`codex`, `pi`, or `claude`), preserves terminal UX, and creates a Unix socket control channel under `~/.local/share/codoxear/socks/`.
- Writes a `*.json` sidecar with: `agent_backend`, session/thread id, pid(s), cwd, log_path, sock_path, owner tag, and launch settings.
- Detects the active session log and keeps `log_path` updated by scanning the process tree for open backend log files (`~/.codex/sessions/rollout-*.jsonl` for Codex, `~/.pi/agent/sessions/*.jsonl` for Pi, `~/.claude/projects/**/*.jsonl` for Claude Code) plus backend-specific resume/discovery fallbacks.
- Ignores Codex sub-agent rollout logs (`session_meta.payload.source.subagent`) so the UI stays bound to the main session.
- Linux and macOS.

### `codoxear.sessiond`

- Headless session helper that can launch a backend session without an interactive terminal.
- Uses backend adapter-owned launch options for Codex, Pi, and Claude Code, including backend-specific model/provider/reasoning flags.
- Writes the same `socks/*.sock` + `socks/*.json` metadata shape the server expects and exposes the same control state schema (`busy`, `queue_len`, `token`, `interrupted_idle`) for readiness/token projection.
- Reuses shared terminal-query responses and backend log busy reducers where behavior should match the broker; it intentionally does not provide a foreground terminal UX.
- Linux and macOS.

### `codoxear.rollout_log` and `codoxear.pi_log`

- Shared normalization layer that turns backend-native logs into the UI’s common event/token/busy model.
- `rollout_log.py` handles chat-event extraction, delivery messages, idle detection, and token snapshots for both backends.
- `pi_log.py` contains Pi-specific helpers for session headers, assistant/user text extraction, final-turn detection, run settings, and context usage derived from Pi `usage.totalTokens` plus `~/.pi/agent/models.json`.

### UI (`codoxear/static/index.html`)

- UI shell served at `/` and `/static/index.html`, with assets under `codoxear/static/`.
- `app.js` is a boot-only entrypoint: it starts service-worker registration before the auth check and chooses login or application rendering. `app_sw.js` memoizes registration of the unversioned `/service-worker.js` through `resolveAppUrl`, preserving `CODEX_WEB_URL_PREFIX`; notifications share that registration, while offline caching does not require notification permission or PushManager support.
- `app_application.js` is the application factory. It validates shared dependencies, creates `app_application_composition.js`, and exposes its rendering surface.
- `app_application_composition.js` owns `renderApp` composition: shell construction, application lifecycle, and controller assembly via `app_wiring.js`.
- **State stores.** `app_session_state.js` is an 8-field observable runtime store (`selected`, `running`, `queueLen`, `subagentsRunning`, `subagentDetails`, `turnOpen`, `sending`, `token`) with `get`/`set`/`subscribe`/`applyRuntime`. `subagentsRunning` and `subagentDetails` are one atomic selected-session snapshot: transcript projection subscribes to both, so detail telemetry refreshes even when the count is unchanged. `app_session_catalog.js` owns the session list (`latestSessions`), derived `sessionIndex`, `recentCwds`, `newSessionDefaults`, and `tmuxAvailable`, with `patchSession`/`applySnapshot` atomic writes. `app_polling.js` owns scheduling via `createPollingRuntime` and a separate `createAsyncEpoch` for cancellation.
- **Widget rule: element + render + subscription in one module.** `app_topbar.js` owns the context chip and interrupt button end-to-end: element creation, rendering, session-store subscriptions, and interactions. The topbar carries **no status chip**: queue depth is shown by the composer queue button badge (the count rides the control that acts on it) and the sidebar session card badge, so `app_topbar.js` never subscribes to `queueLen`. `app_notifications.js` owns notification runtime (`enabledLocally`/`syncState`/`pollFeed`/`dispose`). `app_help.js` owns the help overlay. `app_settings.js` owns the one flat Settings dialog (sidebar Settings button): an Appearance section (swatches, mode, custom CSS — no reset control; every choice is reversible through the same controls) followed inline by the “Voice & notifications” section. That section's nodes, rendering, and Save/Cancel flow stay owned by `app_voice.js` (`createVoiceDom` returns the `<section>`; the dialog mounts it and calls `activateSettingsSection`/`deactivateSettingsSection` on show/hide, while the voice controller opens/closes the dialog through injected `openSettings`/`closeSettings`). There is no separate voice dialog and no drill-down row. `app_theme.js` owns the theme surface. `app_conversation_copy.js` owns the conversation-copy formatter.
- **Wiring.** All controllers receive per-controller `select()` contracts from `app_wiring.js` — no option bags, no spreads. The architecture guard `scripts/check_wiring.py` (7 check types: `pass-through-factory`, `bag-spread`, `direct-bag-argument`, `global-registration`, `select-undercoverage`, `unbound-option-value`, `select-callsite-coverage`) enforces this. Every entry in `scripts/wiring_guard_allowlist.json` requires a reason, and tests pin the exact entry count per check type. Cross-commit monotonicity comes from those reasons, pinned counts, and review; set comparison with the current commit cannot enforce it. New wiring must pass the guard.
- **Modal policy** lives in `app_modal.js` (`createModalPolicyController`, `createConfirmationController`, `createModalKeyboardHandler`). `app_session_display.js` is gone.
- `app_shell.js` owns only the `topMeta`, `titleRow`, and `topActions` layout slots; `app.css` owns presentation.
- Domain modules own file work (`app_file_ops.js`), chat/transcript interaction (`app_chat_interaction.js`), session transitions (`app_session_lifecycle.js`), and session-list refresh (`app_session_refresh.js`); application composition owns cleanup-registered listeners.
- Peripheral controllers keep focused workflows out of composition: `app_message_flow.js` for confirmed-send/SSE/polling, `app_attachments.js` for staged uploads, `app_unattended.js` for unattended mode, `app_composer.js` for composer UI, plus focused transcript, queue, file-viewer, launch, search, and voice modules.
- Supports creating web-owned sessions via the "New session" button with backend tabs for Codex/Pi/Claude Code; **Pi is the default** (overridable via `CODEX_WEB_DEFAULT_AGENT_BACKEND`).
- Remembers the last backend choice and last provider choice per backend in browser local storage.
- Shows backend status icons in the sidebar metadata line and backend logos in the new-session modal.
- Also uses queue, diagnostics, file-read, and git-viewer endpoints for the current UI.

## Data flow (high level)

1. Terminal: `codoxear-broker` runs the selected backend CLI and registers a control socket + metadata file.
2. Server: lists available sockets, reads metadata, and serves session content via `/api/*`.
3. Browser: `app.js` authenticates and delegates to the application factory/composition, which wires focused controllers. Those controllers select sessions, send prompts via `/api/sessions/<id>/send` or `/enqueue`, render normalized messages from the backend log over SSE with polling fallback, and read files/git state through `/api/sessions/<id>/*` helpers.

## Current frontend and runtime state

- **Frontend ownership is store-driven.** `app.js` is boot-only; the factory and `renderApp` composition are separate. Mutable session-runtime state lives in `app_session_state.js` (7 fields); session-list/defaults state lives in `app_session_catalog.js` (derived `sessionIndex`, atomic `applySnapshot`). Rendered values are owned by widget-internal store subscriptions — not cross-module renderer calls. Reducers write stores atomically (`applyRuntime`/`applySnapshot`/`patchSession`); imperative cross-module renderer calls are an anti-pattern the wiring guard and reviews reject. Controllers receive per-controller `select()` contracts from `app_wiring.js`.
- **Frontend teardown invariant.** Codoxear treats `beforeunload` as unconditional full teardown (`cleanupApp` empties the app root), so no feature may initiate a same-tab navigation. Downloads must use `a[download]` (or a fetch/blob handoff), because a navigation converted to a download still fires `beforeunload` and blanks the app.
- **Sent-prompt journal is write-ahead and covers every submission.** `codoxear/send_journal.py` appends a per-session JSONL journal under `<app_dir>/send_journal/<session_id>.jsonl`: a fsync'd submit row (committed text + display text + attachments) BEFORE broker dispatch in `SessionSendCoordinator.send` and at enqueue time in the queue coordinator (keyed by the queue item id, so dispatch adds only the outcome row), followed by an outcome row (`ack`/`commit_unknown`/`error`). A confirmed send can be eaten by the backend (a Pi modal dialog did exactly this) without reaching the backend log — the journal is the recovery record of last resort, rotation-capped and removed only on explicit session delete. Journal faults never block a send; they surface as `send_journal_error`. `GET /api/sessions/<id>/sent-history?cursor=&limit=` serves newest-first entries for the composer's ArrowUp recall: empty composer + ArrowUp (picker closed) enters recall mode in `app_composer_history.js`, repeated ArrowUp walks older entries with cursored lazy fetch, and any other key, pointer interaction, or cursor move exits, leaving the recalled text as the normal draft buffer; recall never fires with a non-empty composer, so drafts cannot be clobbered.
- **Send path is unconditional confirmed-send.** The busy/queue gate was removed: `require_send_preconditions` only blocks on commit-unknown resolution, a pending attachment, a stale queue item, or missing broker `sync_send`. Direct sends submit regardless of busy state, so steering works on all backends. The queue remains an opt-in alternative, not a hard gate. The offline gate described below and an attachment gate sit in front of this: `sendText` refuses while the attachments controller reports in-flight uploads (`hasPendingUploads`), because an optimistic pending upload is invisible to both the local staged list and the server `pending_attachment` flag, so an ungated send would silently drop the file.
- **Undelivered prompt recovery.** A confirmed send is a bet: accepting the PTY write does not mean the backend acted, and a startup gate or modal can eat the whole prompt. The broker publishes that lost bet rather than only resetting busy. An idle-origin, non-slash send carries a browser-supplied `send_id`; when its turn-aware send latch settles with zero turn activity (`latch_settled_idle` in `_mark_busy_state_idle`), the control `state` response carries `send_verdict = {"send_id", "verdict": "undelivered", "ts"}`. Zero turn activity only proves a swallow when the backend could record a turn, so two rules guard the settlement: Pi's working indicator (default message `Working...`, plus OSC `9;4;3` when Pi's terminal-progress setting is on) counts as turn activity, because a fresh Pi session buffers every entry and writes its session file only at the first assistant message (so a first prompt with a slow first reply has no row to observe while Pi is demonstrably at work), and the quiet window starts no earlier than first readiness — a bound log, or the pid-validated bridge marker written from `session_start` — so a send injected while the TUI was still booting is not judged from its injection time (`send_latch_window_start_ts`, `mark_backend_ready`). Delivered sends, busy-origin steering sends, and slash commands never arm it (no new turn could exist to miss), and a published verdict survives later sends, replaced only by a later swallowed one, because it names one submission. The server parses it strictly (`broker_send_verdict`), mirrors it onto `Session.send_verdict` in `get_state`, exposes it on the public listing row, and `POST /api/sessions/<id>/send` forwards an optional `send_id` into the broker request. Client-side, `app_message_flow.js` records an outstanding delivery before the POST (its `catch` deletes it because the composer keeps the text on a transport failure), and a catalog row whose verdict names that id retracts the optimistic echo (`dropPendingUser`/`removePendingUserRow`), clears the optimistic busy state, and calls the composition's `restoreUndeliveredDraft` seam. That seam writes through the composer's single `setDraftFromServer` writer plus `noteDraftEdited` (a server-draft write like any typed edit) and refuses to clobber a non-empty draft, where the toast instead points at the empty-composer `↑` recall. Records are deleted on match, so a repeated snapshot is inert and a reloaded page (which holds no matching record) ignores an old verdict. Latency is inherent: the verdict cannot exist before the 3 s quiet window elapses, and it reaches the browser on the next session-list poll (`scripts/docker_undelivered_send_verify.sh` measures ~8 s from Send click to restored draft). Not covered: attachments on a swallowed send, and queue-dispatched sends (no client send id); the send journal plus `↑` recall remains the recovery record there.
- **Attachment staging is optimistic.** `app_attachments.js` registers local-only pending-upload chips synchronously at `stageFiles` entry (object-URL thumbnail, compressing/uploading phase with a pulsing dot, AbortController-backed cancel), swaps each to the authoritative staged chip in the same tick its `inject_file` response commits, and keeps the thumbnail in a page-lifetime `localThumbs` map pruned by the single render funnel. Failures hold a danger-bordered error chip ~2s. The server staged list stays authoritative; pending entries never merge into it, and a selected-session change aborts and clears them.
- **Live transcript delivery uses SSE.** `app_message_flow.js` owns confirmed-send and shared live transcript transport. Once a session is selected and bound to a backend log, it opens an `EventSource` on `/api/sessions/<id>/live` (`message_routes.py` `handle_messages_live_stream`) for real-time message deltas; HTTP polling is the automatic fallback. Both paths share one live-delta projection (`_project_live_record_window` in `message_routes.py`), so they produce identical transcript state.
- **Offline PWA reading uses the service worker.** `service-worker.js` owns three Cache Storage caches: `codoxear-html-v1` (navigation network-first with an `onLine === false` cache fast-path and a 3-second network race, offline match ignores the query), `codoxear-static-v1` (versioned `?v=` assets cache-first, pruning other versions of the same path after a successful put; unversioned assets stale-while-revalidate), and `codoxear-api-v1` (same-origin GET APIs use the same fast-path + 3-second race with exact-request offline fallback). An offline hint skips fetch only on a cache hit; cache misses still attempt the network. Timed-out fetches continue under `waitUntil` so a late success refreshes the cache. This bounds delivery even when airplane-mode + VPN tails or captive portals hang instead of rejecting; the shell's boot watchdog waits 12 seconds after page load so sequential offline boot API timeouts fit before the failure panel. Without the network-suspect latch, `onLine === true` and every request hanging made navigation → `/api/me` → `/api/sessions` → transcript tail cost four 3-second races (~12 seconds from reload, ~9 seconds after navigation); the watchdog starts after navigation, not at reload. After a network-first timeout or rejection, the worker serves cache immediately for 30 seconds while revalidating in the background; any successful network response clears this network-suspect latch. Static cache-first/SWR behavior is unchanged. Only status 200 responses enter the caches; 401, 304, and other failures never replace them. The SSE `/api/sessions/<id>/live` route is pure passthrough, as are non-GET and cross-origin requests. Routing uses paths relative to the registration scope, so prefixed deployments retain the same policies and SSE exclusion. Install calls `skipWaiting`; activation removes obsolete `codoxear-*` caches and claims clients. Offline cold-load reuses previously fetched shell, authenticated `/api/me`, session list, and message-history responses through the existing API/store contracts — no second frontend state writer or auth-flow branch. SW activation warms the shell, versioned assets, `/api/me`, and `/api/sessions`, so one authenticated online visit after a deploy suffices for the app to cold-load offline; per-session transcripts still cache on use and must have been opened online, and uncached requests still fail offline. On a fresh or expired-cookie profile, successful login best-effort waits for SW readiness (bounded to 2 seconds) and refreshes `/api/me` before rendering the app, so the activation-time 401 is replaced by a cacheable authenticated response. Because the theme link is generated dynamically, warm-up synthesizes versioned URLs for the explicit paper/clay/slate family list; the activation behavior test checks this list against every stylesheet in `static/themes/`. `sendText` and queue enqueue refuse when `browserOffline(navigator)` is true, toast “Offline — reconnect to send.” / “Offline — reconnect to queue.”, and preserve the composer. There is no outbox or deferred-send machinery; the existing network banner remains the only offline indicator. Service-worker navigation markers are recorded in the `codoxear-sw-meta-v1` cache and can be inspected through browser devtools’ Cache Storage.
- **Full-transcript search is server-side.** `app_chat_search.js` queries `/api/sessions/<id>/search`; `message_routes.py` searches the normalized backend log and returns cursored matches so selecting a match can load its surrounding history.
- **Pi subagent activity has two projections.** `pi-subagent:` events become inline narration rows, while `util.scan_active_pi_subagents()` supplies one record per actually running lifecycle-v3 child (parallel siblings remain distinct; pending future chain steps do not count). Child identity is the **run record**, not the workflow step: pi-subagents runs every async workflow child as its own process with its own `async-subagent-runs/<runId>/status.json`, and the workflow root's `steps[i]` entry is only a mirror of it, so the mirror is never projected as a second child (projecting both reported a K-lane fanout as 2K). The record is authoritative for both identity and liveness — its own pid gate, and its own state, which is why a running step mirroring an already-settled child reports nothing. A step that names no run record (in-process host step) or whose record cannot be read still projects from the parent, and a workflow root itself is never a child, so a root with no step statuses projects no row. The sidebar shows only the compact `▸N` marker. The transcript's busy typing bubble and idle activity bubble both show the compact summary plus one automatically visible line per supplied active child; there is no disclosure toggle, popover, or synthesized “unknown” row. Each bubble is intrinsically content-sized up to the normal transcript-bubble maximum, and detail lines wrap rather than widen or clip the row; the marker (dots/squares) and summary label share one dedicated header row so detail width can never displace the label from its marker. Each line includes only producer-backed role/model/tool telemetry, removes a provider prefix from qualified `provider/model` names, and labels cumulative usage `tokens`; per explicit user preference these detail lines use `var(--font-ui)` — the one sanctioned exception to the mono-for-data rule — so they match the summary's family at a smaller size.
- **Typing, thinking, and subagent indicators share one explicit reconciliation model.** `rollout_idle.py` accumulates Codex cumulative reasoning snapshots, Pi reasoning-token usage, and Claude Code thinking-token usage into `thinking_tokens`; `app_transcript.js` renders a token count only when it has positive authoritative token data. Live tool/thinking deltas are exact; while a turn remains open, resumable session snapshots may only raise those counters, never lower them. `subagents_running` and `subagent_details` are the selected session's atomic current-liveness snapshot: both may change in either direction, and detail-only catalog updates must refresh both transcript activity bubbles even when the count is unchanged. They must never be folded into the monotonic tool/thinking counters.
- **Slash completion and live controls are backend-aware.** Typing `/` shows browser-safe commands from `slash_commands.py`. The Pi menu is always a **union**: curated browser-safe builtins plus the bridge's live registry snapshot (extension commands, templates, skills) with interactive entries filtered from the extras only — never a replacement, because Pi's `getCommands()` is the extension registry and cannot contain builtins. The bridge preserves its registry snapshot across caps refreshes (a settings-changing rewrite must not drop it) and retries command registration on `turn_end`. Pi `/model` uses its shared TUI command; Pi `/effort` (with `/thinking` alias) is bridge-provided; Pi `/new` is advertised because the transcript replacement boundary (see "State-authority principle") renders its effect correctly, while the other session-lifecycle commands (`/resume`, `/fork`, `/clone`) stay hidden because their TUI flows pick targets interactively. Claude Code `/model` and `/effort` pickers inject its native commands. Capable Codex sessions run their TUI against a broker-owned app-server Unix socket; `/model` and `/effort` call the typed experimental `thread/settings/update` API, while unsupported Codex versions advertise neither command.
- **New-session comboboxes are pickers, not text prefixes.** Opening the provider/model list (click on the field, or ArrowDown/Up while it is closed) clears a committed pair and lists every configured option — recents first, then one sticky group per provider — while a non-empty query keeps the ranked 12-item filter; the first edit of a committed pair replaces it instead of appending to `model · provider`. Opening the cwd list clears a committed path and lists every recent directory (no 10-item cap, and no filesystem-root scrape that an empty path would otherwise add), but typing still edits the path in place, because a path prefix is a meaningful query (`/src` drills into the shown directory). For both, a browse-only open that ends without a selection restores the value verbatim (blur, outside click, Escape, Tab, sibling menu) and `start()` restores before parsing, so browsing can never launch a different model or directory; a typed value survives those same dismissals. `renderModelMenu`/`renderRecentCwdMenu` are the only renderers and `dismissModelPicker()`/`dismissCwdPicker()` the only closers — a new close path that bypasses them strands an empty field.
- **Markdown renders raw `<video>` HTML with resolved sources.** marked passes video markup through verbatim; `rewriteMarkedVideos` in `app_markdown.js` then routes each `src`/`<source src>` through the same local-ref → `/api/sessions/<id>/file/blob` pipeline as images (the blob response already supports Range/206 for seeking), forces `controls`/`preload="metadata"`/`playsinline`, and rewrites `poster` through the image resolver. Only browser-decodable containers (mp4/m4v/webm/ogv/ogg, mirroring the file viewer's `BROWSER_SAFE_VIDEO_TYPES`) stay inline; anything else collapses to plain path text, which the file-ref pass upgrades to a clickable viewer link where the transcoded compatible preview lives.
- **Markdown preserves line breaks and image geometry.** `app_markdown.js` calls `marked.parse(..., { breaks: true })` and caches rendered image dimensions in local storage. Strikethrough is GFM-strict: a tokenizer override in `app_markdown.js` pins the del rule to exactly `~~` per side (marked v15's builtin also accepts single `~...~`, which falsely paired approximation/range tildes like `100~300` and `~50` into strikethrough spans), so a lone `~` always renders literally.
- **Markdown autolinks end at CJK prose punctuation.** marked's GFM extended autolink scans a URL candidate to the first whitespace or `<` and trims only ASCII trailing punctuation, so a bare URL followed directly by prose punctuation swallows it — `…/dexgem-strategy（私有，jackw1997 邀请已发）` becomes one anchor (cmark-gfm/GitHub renders the same HTML; CJK prose has no inter-word spaces, so this is the common case for agent output, not an edge case). `app_markdown.js` registers an inline extension (`ensureCjkUrlBoundary`) ahead of the built-ins that ends the candidate at the first non-ASCII `\p{P}`/`\p{S}` code point — the table marked itself uses for `_punctuation` — and hands the truncated candidate back to marked's own `url` tokenizer, so GFM's trailing-punctuation trimming stays marked's. It must be an `extensions` entry, never a `use({tokenizer: {url}})` override: measured, an override returning `undefined` suppresses the built-in with no fallthrough (`false` is that path's fall-through signal), which would force reimplementing marked's URL body. Non-ASCII letters and digits never terminate a link, so CJK paths and query values (`…/wiki/中文`, `?wd=萧山人工智能`) keep working; ASCII URL punctuation stays governed by marked; percent-encoded forms (`%EF%BC%88`) are untouched; and the email branch, explicit `[label](dest)`, `<dest>` autolinks, and code spans keep their literal destination. `tests/test_markdown_cjk_autolink.py` pins the boundary rule and every path that must keep marked's output.
- **Previewable documents open in preview, not in source.** `resolveFileOpenMode` (`app_file_viewer_controller.js`) resolves an open in this order: an explicit caller mode, then a git-changed diffable candidate → `diff`, then a previewable document kind (`markdown`, `html`, via `isPreviewableFileKind` in `app_file_helpers.js`) → `preview`, else `file`. The per-kind default is the loaded document kind, never the remembered viewer mode; `codexweb.fileNonDiffMode` now only remembers the non-diff mode to return to when leaving diff, and `fileViewMode` remains the current mode. The same document-kind predicate exists as a path form (`isPreviewableFilePath`) for the pre-load clamp in `resolveFileOpenViewMode` and for the mode-choice decision; both extension sets live in `app_file_helpers.js` and are pinned against `codoxear/file_types.py` by `tests/test_file_preview_default.py`. Line-targeted transcript references (`doc.md:120`) still open in source — only source shows a line — so `showFileViewer`'s `mode` is forwarded through `app_file_viewer_lifecycle.js` into `openFilePathWithResolvedMode` as the explicit requested mode; a plain reference passes no mode and gets the kind default. The file picker's changed-file rows pass `changed`/`gitPath` and still open as diffs. The one deliberate exception is the new-file/draft input (`openDraftFilePathWithGuard`), which opens an existing path in source because that flow is create/edit, not default-open. The default is intentionally not a remembered preference: no stored value can flip a later document to source, and a user's source-view choice applies to the file in view until it is closed (the toggle re-renders the same document).
- **HTML preview is a sandboxed same-origin frame; the sandbox is load-bearing.** `.html`/`.htm` files get server kind `html` and render in `iframe.fileHtmlPreview` (`app_file_viewer.js`) whose `src` is the server-provided `preview_url` → `GET /api/sessions/<id>/file/raw/<path>`. The route serves the document (and its relative subresources, so the browser resolves `img/…`, stylesheet `href`, and CSS `url()` natively against the document's real directory) with an extension-derived MIME type, `X-Content-Type-Options: nosniff`, and, for executable document types (`text/html`, `application/xhtml+xml`, `image/svg+xml`), `Content-Security-Policy: sandbox allow-same-origin` so a direct navigation to that URL is inert too. The iframe must keep `sandbox="allow-same-origin"` and must never gain `allow-scripts`: the app is single-user, cookie-authenticated, and the same origin serves its own API, so script execution would let a session-cwd document act as the user (read transcripts, delete sessions, send prompts). `allow-same-origin` is required rather than optional — with `SameSite=Strict`, an opaque-origin frame receives no auth cookie and every relative subresource 401s. Scripts therefore never run in a preview: an HTML page that depends on JS renders its static form, the status line reads `preview (scripts blocked)` so an inert page does not read as a broken preview, and an html result without `preview_url` falls back to source with a `preview unavailable` status instead of an empty frame.
- **Theming.** Three families (clay/slate/paper) × light/dark, default clay + follow-system, chosen per device in the Settings dialog and applied by `app_theme.js`. See the “Design language” section below for the cross-theme invariants, the theme file contract, and each family’s rules. `<meta name="theme-color">` is written twice by design: the inline boot script in `index.html` projects the stored family×mode before first paint (its six-value table duplicates `THEME_COLORS` in `app_theme.js`; `tests/test_theme_boot_script.py` executes the script and pins the tables equal), and `app_theme.js` rewrites it on every live apply. iOS Safari applies theme-color to its status bar on navigation, not continuously, so a live theme switch's status-bar color catches up on the next load — platform behavior, not an app bug.
- **Performance.** Static asset responses are gzip-compressed (`static_routes.py`), served over `HTTP/1.1` (`server_handler.py`), versioned assets (`?v=...`) get immutable one-year cache headers, the asset version is memoized, and poll cadence is tuned via `CODEX_WEB_*_INTERVAL_SECONDS` env vars. Every static response also carries a weak `ETag` and honors `If-None-Match` with 304, so unversioned URLs revalidate without re-downloading. Non-HTML assets use the fast stat-based validator; HTML responses hash their final substituted bytes (asset version + attachment limit), because a release that changes only assets leaves `index.html`'s stat untouched while the served representation changes — a stat validator would 304 a changed HTML and pin clients to immutable old asset URLs. Monaco's AMD loader is configured with `urlArgs` set to the asset version (`createMonacoLoader` in `app_file_editor.js`), so every loader-fetched module (editor chunk, css, nls, per-language contributions) is versioned and immutable-cached; Monaco's internally computed worker URLs cannot carry the version and rely on ETag revalidation instead. The lazy PDF.js module and worker (`createPdfLoader` in `app_file_viewer.js`) get the same version query. KaTeX font URLs are CSS-internal and unversioned; they rely on ETag revalidation.
- **Session card DOM has two branches and must stay split.** Touch uses swipe actions; desktop uses hover-revealed actions (`useDesktopSessionActions()` / `swipeActions` flag in `app_session_helpers.js`). Do not attempt to unify them into one branch.
- **Keyboard.** Vimium-style hint mode: press `f`, then the letter over an activatable control in the current viewport. Hidden, off-screen, disabled, or hit-test-covered controls receive no hint. Direct shortcuts (no leader): `i` focus message, `j`/`k` scroll, `d`/`u` half-page, `G` go to bottom, `D` delete session, `/` full-transcript search. Typing `/` in the composer opens slash-command completion. Typing a whitespace-delimited token starting with `./`, `../`, or `~/` (any caret position) or `/` (token not at message index 0) opens file path completion in the same picker, backed by `GET /api/sessions/<id>/file/complete` (`file_complete.py`): the endpoint lists the token's directory (resolved against the session cwd, expanduser, or absolute), fzf-ranks entries against the trailing fragment via `file_search_score`, and returns prefix-preserving completions; directories drill down, files accept, Enter and Tab accept, and the open completion session anchors its span so filenames with spaces complete without quoting. The composer height control (`expandBtn`, hint `j`) is a grabber strip across the composer's top edge — it appears once the draft overflows the normal cap (or a non-normal height mode is active) and keeps the input row's horizontal space untouched. Click cycles normal → tall (fixed height) → full (composer takes the whole main column, transcript collapses); dragging the strip vertically resizes continuously, snapping to normal/full at the thresholds. The mode is remembered per session in browser local storage and a successful send/enqueue returns it to normal. The topbar interrupt button (`interruptBtn`) is the sole interrupt control on all viewports with hint `z`; the composer stop button was removed. On Pi sessions, `/model` uses Pi's native selector and the bridge registers `/effort` with `/thinking` as its alias; old live sessions need `/reload` or a restart before the capability is advertised. On Claude Code sessions, the `/model` and `/effort` pickers inject native commands; model rows refresh only from subsequent assistant `message.model` log evidence, while effort has no parsed CC log evidence and stays at its launch value. In open dialogs, the first distinctive letter of a visible button activates it, with a later distinctive letter breaking first-letter ties (`activateModalButtonForKey` in `app_modal.js`, bound by `app_chat_interaction.js`). **Escape never closes or cancels a modal dialog** (user-stated rule): transient modes keep their Esc exit (hint mode, dropdown menus, composer model picker, composer blur, touch selection), and dialogs close only via their buttons, backdrop, or hints.
- **Monaco follows the UI theme.** `app_file_editor.js` defines six Monaco themes (`codoxear-<family>-<mode>`, from one data table; `paper-light` is the original GitHub-light surface and a regression surface) and `monacoThemeName(family, mode)` maps a theme snapshot's `family`/`resolvedMode` to one. The theme store is the sole writer of the active name: `createMonacoLoader` takes an injected `subscribeTheme(fn)` (the composition passes `themeController.subscribe`), remembers snapshots that arrive before Monaco loads and applies the current name at init, and calls `monaco.editor.setTheme` on later snapshots. Editor and diff-editor creation always pass the loader's `currentThemeName()` — Monaco's theme is global, so creating an editor with a constant name would flip every surface back to light. `scripts/docker_theme_verify.sh` checks the live switch against real Monaco.
- **File viewer vim layer** (`app_file_vim.js`). While the viewer is open, a document-capture keydown listener (registered before `bindFileEditorInteractions`) owns vim keys: motions `h j k l w b e 0 $ gg G Ctrl-d/u` on Monaco surfaces (cursor commands; `cursorMove by halfPage` for half-page), scrolling on cursor-less surfaces, insert entries `i a A o O`, verbs `x dd u Ctrl-r`, and `f` → hint `enter()` (explicit, because Monaco's hidden textarea otherwise blocks hint activation). Edit mode starts in insert; Esc goes insert → normal → (clean buffer only) view; the vim normal sub-mode makes `activeFileEditorWritable()` false so the editor stays read-only, and verbs temporarily lift `readOnly` to mutate. Direct letter activation of viewer buttons is replaced by `f`-hints while the viewer is open (unconsumed printable keys are swallowed by the vim layer).
- **Codex control authority uses the TUI's app-server thread.** The broker probes experimental `thread/settings/update`; on capable Codex versions it starts a private app-server Unix socket and launches the same shared TUI with `--remote`. Browser model/effort choices go through broker control to that typed API, never through PTY picker navigation or config+signal reload. The sidebar remains `turn_context` log-authoritative and updates after the next turn records the effective settings. Unsupported versions continue with embedded TUI mode and do not advertise the controls.
- **Pi launches always pass `--approve`.** Pi's project-trust dialog (triggered by `.agents/skills` or `.pi/` resources in the project tree) is a modal the web UI cannot see, and it silently consumes injected sends — an unanswered dialog once ate an entire confirmed prompt. `_ensure_pi_approve_args` appends `--approve` to every Pi argv codoxear builds (broker and sessiond paths), gated by a once-per-process `<pi> --help` capability probe because older Pi versions exit hard on unknown flags. The user's global `defaultProjectTrust: "always"` covers non-codoxear runs; per explicit user decision the trust prompt is treated as a rubber stamp to suppress, not a consent step to surface.
- **Pi control authority goes through an extension bridge, not web-only RPC.** Codoxear wraps all backends in a PTY so web and terminal share the same session; Pi `--mode rpc` is a separate headless mode that cannot coexist with the TUI. The bridge supplies Pi effort control from within the live TUI process, while Pi `/model` remains its shared native command. See `.memory/project/ARCHITECTURE.md` “Pi integration strategy” for details.
- **Pi bridge lifecycle rule.** Extension load may write its passive capability marker and register lifecycle listeners, but it must not call runtime action methods at load. Defer command registration and runtime queries until `session_start`/`session_switch`, when Pi has a live session context; retry a failed registration from a later lifecycle event.
- **Send busy-latch and /new materialization contracts.** The broker latches `busy`/`turn_open` optimistically on every confirmed send, betting the backend writes a turn to the bound log; the latch records the log offset and the turn-activity baseline (`send_latch_activity_ts`) at send time, and the idle sweep clears it when no reducer-observed turn row appears within the quiet window. The bet is turn-aware, not byte-aware: non-turn rows such as Pi `model_change`/`thinking_level_change` grow the log without opening a turn and must not hold the latch (`/model`, `/effort`, `/new`, `/reload` all settle). A latch that settles with zero turn rows since the send re-establishes the interrupted-idle projection, because the log tail may still be non-final from an earlier errored turn while the TUI is demonstrably settled at its editor. A binding switch closes an unfulfilled latch whose new-log seed shows no open turn. Pi defers creating a new session's log until the first assistant row, so the bridge pre-flushes Pi's own header object (and flips the manager's `flushed` flag) on lifecycle reason `new`, letting the broker rebind at `/new` time instead of at the first message. While no log is bound the broker's `_log_watcher` still runs the idle sweep on its 0.25s timer (`_mark_idle_if_quiet`), because a swallowed first send produces neither log growth nor PTY output and would otherwise hold the latch forever (observed stuck ≥ 40 min).
- **Backend: ordered log-derived projection.** Log-derived session state (busy, tokens, model, effort) commits through one ordered, log-identity-aware boundary: `LogDerivedSessionObservation` in `session_log_projection.py` committed via `commit_log_observation` in `session_log_runtime.py`. Poll and SSE share one live-delta projection (`_project_live_record_window` in `message_routes.py`). `SessionManager` uses a retained coordinator graph with focused dependency records (`SessionManagerCoordinatorDeps` in `session_manager_factories.py`) — no mega-caps, no `*args`/`**kwargs` forwards.
- **Session snapshot (save/restore-all).** `session_snapshot.json` in the app dir records each live session's launch config for respawn-after-death. Entries are keyed by **transcript identity** `(agent_backend, thread_id)` — never by the registry session id (the broker sidecar's sock stem, `broker-<pid>`), because pids are reused after a reboot; each entry records its current registry id plus the broker's `start_ts`, and the pair names one broker incarnation. Upsert supersedes in three directions (`session_snapshot.py` docstring): same transcript under a new registry id (resume landed — fires the queue/draft/alias/UI-state/dependency remap and clears any restoring mark), same incarnation under a new transcript (Pi `/new`), and a new thread declaring the stored thread as its resume target. Writes are **upsert-only**: auto-save triggers on discovery signature diffs (`session_snapshot_runtime.py`, debounced with bounded retry), and entries are removed only by explicit events — UI delete, `DELETE /api/sessions/snapshot/<id>`, clean broker exit (the broker unlinks its sock+sidecar only when the agent exits 0; a crash leaves them and produces a lost tombstone, which keeps the entry), or a restore that finds the transcript permanently gone. An upsert that would empty a non-empty snapshot is refused. The queue sweep exempts snapshot-referenced session ids so queued work survives a server restart. Restore (`session_snapshot_restore.py`, `POST /api/sessions/snapshot/restore`) respawns entries through the web launch path with a trusted `resume_row` (`session_launch_plan.py`) that bypasses the cwd candidate scan but re-derives the row from the transcript log and keeps the live-target guard; it marks entries `restoring` (10-minute expiry) instead of consuming at launch, fails loudly when tmux was recorded but is unavailable, and isolates per-entry errors. The UI is a single contextual dashed restore row (`app_session_snapshot.js`) pinned above the session list in its own lead host — the sessions controller owns every child of `#sessions` and clears it per render, so the row must NOT live inside that container; its feed refetches `GET /api/sessions/snapshot` when the catalog liveness key changes or after a 60s cadence floor, evaluated only on catalog generations — never a new polling loop.

## State-authority principle

Every displayed state has one declared authoritative writer. Rendered values are owned by widget-internal store subscriptions in the owning module; reducers write stores atomically (`applyRuntime` in `app_session_state.js`, `applySnapshot`/`patchSession` in `app_session_catalog.js`). Imperative cross-module renderer calls are an anti-pattern — the wiring guard (`scripts/check_wiring.py`) and reviews reject them. A widget owner renders initial state at construction through the same writer function its subscriptions call: one rendered value has one writer function, invoked at construction and on change. When multiple feeds can update one displayed value, the owning module must document the reconciliation rule and make it explicit in code; do not add a second cache or derive the value independently. The typing row is the canonical dual-feed case: live SSE deltas are exact, session-list snapshots are resumable, and while a turn is open the snapshot can only raise counts in the shared `typingRowRuntime` store.

The typing/activity bubble is another dual-field case: the session-list catalog supplies current child count plus child records, `app_session_state.js` commits `subagentsRunning` and `subagentDetails` atomically, and `createTypingRowStoreProjection` is the only renderer trigger. Both busy and idle bubbles use the same detail formatter and automatically show only supplied records; no renderer pads a count mismatch with placeholder rows. A session switch clears both fields together.

Focus-ring visibility under script-driven focus has one modality writer. `createInputModalityController` (`app_modal.js`) is the sole writer of `<html data-input-modality>` (`keyboard` after any capture-phase keydown, `pointer` after any pointerdown, initial `pointer`), registered through the composition's cleanup-tracked `addAppEvent`. `app.css` keys the keyboard-modality `:focus` ring on that attribute (scoped with `:where()` so the composer-textarea and `[tabindex="-1"]` no-ring rules keep winning), so a dialog's script-focused default button rings exactly when the dialog was opened by keyboard — the browser's `:focus-visible` heuristic is never a second writer for script-driven focus.

Transcript replacement has one boundary, and it is keyed on log identity, never on recognizing a typed command. When a same-session tail fetch in `openSession` returns a `bound` snapshot whose key (thread id + log path) differs from the rendered transcript's key — the previous bound key on a direct rebind, or the renewal marker's `ignoredKey` after `beginTranscriptRenewal` — the backend has discarded the old working context (Pi `/new`, `/resume`, `/fork`, or a terminal-initiated renewal) and the fetch already holds the replacement content, so `openSession` replaces the DOM with the new tail and invalidates older-load state. A transient `pending_bind` snapshot without a rendered key carries no such proof and must keep the preserve path — same-session reloads otherwise never clear rendered rows. This covers renewals initiated from the real terminal, which command-spelling checks can never see.

Pi defers persistence for a fresh session: `/new` allocates the new session file's path immediately but writes the file only on its first entry, so the broker (which requires the file to exist before binding) rebinds when the new session receives its first message — that is when the transcript visibly clears, not at the moment `/new` is sent.

User-message navigation has one owner for resolve → materialize → scroll: `materializeNeighbor` in `app_chat_navigation.js`, fed by the first-class `GET /api/sessions/<id>/messages/neighbor` endpoint (never a degenerate search query). The neighbor request's anchor is the **rendered window boundary** — the first (previous) or last (next) rendered row of any role that carries a `history_cursor` — never the nearest rendered user row: the server resolves the first user message strictly before/after that byte position, and a window whose loaded range contains no user rows (a long assistant tool-run tail) still has valid boundary anchors. The materialization rule, dictated by the transcript store's asymmetry (anchored at the live tail, pages backward only): (a) target already rendered → scroll; (b) previous-direction and `same_log` → bounded incremental prepend preserving the live tail, falling through on exhaustion; (c) everything else (next-direction misses, cross-log targets, prepend exhaustion) → detached window load at the target cursor. The search endpoint remains legitimate only where a total count is needed.

## Design language

The UI ships three theme families — **clay** (default), **slate**, and **paper** — each in light and dark, selected per device from the Settings dialog (`app_settings.js`) and applied by `app_theme.js`. The rules below split into cross-theme invariants every family must keep, and per-family languages a theme may express. Invariants are not preferences.

### Cross-theme invariants

- **Tokens carry appearance; components carry structure.** Every color is a `:root` token in `app.css`; geometry, type, focus, icon muting, and elevation go through `--radius-control`/`--radius-card`/`--radius-bubble`/`--radius-pill`/`--radius-dot`, `--font-ui`/`--font-prose`, `--focus-ring`, `--icon-muted-filter`, and `--shadow-pop`. Base `app.css` is paper light; it contains no color literal outside `:root` (custom-property values excepted) and every base radius resolves to `0`. A component rule in `app.css` must not hardcode a value a family would retune.
- **Typeface is family-invariant.** Fonts are not a family language: every theme renders through the base font tokens declared once in `app.css` (`--font-ui: sans-serif`, `--font-prose: var(--font-ui)`, so markdown headings inherit the UI face). A theme file must not redeclare `--font-ui`/`--font-prose` or set its own `font-family`; the token-coverage geometry guard is mirrored by a family-stylesheet font guard in `tests/test_theme_token_coverage.py`. Families retune color, geometry, focus, and elevation only.
- **Layout geometry is shared.** Spacing uses the `--space-1` through `--space-7` ladder (`4px, 6px, 8px, 10px, 12px, 14px, 16px`); type uses `--font-2xs` … `--font-3xl` with the form-dialog role assignments (`--font-md` chrome, `--font-lg` content/titles, `--font-sm` hints; `--font-xl` only as the coarse-pointer anti-zoom floor). On coarse/small viewports (`@media (max-width: 880px), (pointer: coarse)`), form-dialog type planes retune as a unit — `.formViewer` sets `--font-sm/--font-md/--font-lg` to 13/14/16px — so the 16px entry floor never exceeds the section-title plane: title and entry share 16px and differ by weight, labels sit at 14, hints at 13; desktop planes are untouched. Data-like text (models, tokens, paths) is `--font-mono` in every family, with one sanctioned exception: per explicit user preference, the per-child detail lines inside the busy/idle transcript activity bubbles render in `var(--font-ui)`, matching their summary.
- **Dialog scroll bodies share one gutter.** A scroll container clips ink overflow at its padding box, and focus outlines (2px + 1px offset) paint outside a control's border box. Every dialog scroll body (`.formBody`, `.helpBody`, `.queueList`) carries one grouped treatment: 3px padding on every side (absorbs the ring), a `--space-3` right lane for overlay scrollbars, and `scrollbar-gutter: stable`. Grids and rows inside those bodies do not add their own outset padding (`.choiceChips` keeps its 2px because it is its own scroll container). The Details table (`.detailsGrid`) and file-viewer document surfaces carry their own row/content inset and are not bare scroll bodies.
- **Textareas are classified, never squashed by default.** The bare `textarea` element rule carries no height/resize/overflow; the single-line start and auto-grow contract lives only on `.composer textarea`. Dialog textareas share one multi-line treatment (`.formViewer textarea`: rows-driven height, `min-height`/`max-height`, `overflow-y: auto`, `resize: vertical`), and every other textarea (`.queueText`, `.filePasteInput`, `.unattendedMenu textarea`, `.filePlainEditTextarea`) declares its own sizing.
- **Hit area is not visual size.** 44px touch targets everywhere; compact secondary controls use an `::after` hit area, frequent primary composer/dialog actions may use the larger visible control.
- **State dots discriminate by fill and motion, never by hue.** Busy is filled + pulse, idle hollow, suppressed/snoozed/blocked filled without pulse, pending/starting filled amber + pulse; an active session inverts ink and paper (hollow paper ring when idle, paper-filled when busy/suppressed, amber when pending). A family may round the dot (`--radius-dot`) but may not change these semantics.
- **Transparent, undimmed backdrops** and **bounded overlays**: opening an overlay never dims the app; pickers and dialogs have deliberate max dimensions and scroll only their content area. Diagnostics rows may stack at narrow widths without changing treatment.
- **Single writer per displayed value.** `app_theme.js` is the only writer of `<html data-theme>`, `<html data-mode>`, the theme `<link>`, the custom-CSS `<style>`, and `<meta name="theme-color">`; the inline boot script in `index.html` renders the same persisted state (including the theme-color) once before first paint. Settings only renders controller state and forwards intent.
- **Checkboxes are one component.** `.checkField` is the only checkbox row; its box is 16px with a 1px `--border` ring and `--radius-control` corners, the checked state fills with `--accent`, and the check glyph is an SVG mask in `--on-accent` (never a text "✓" — text glyphs are font-dependent). The 44px target lives in the `::after` lane; the visual box never carries it. Duplicated checkbox styling in another class is a defect — extend `.checkField`.
- **Hover-reveal groups must not use `:focus-within`.** Reveal on `:hover`, keep keyboard access with `:has(<group> :focus-visible)`, and give hover-revealed controls over text an opaque `background: var(--paper)` fill.
- **Layered components self-round; never rely on an ancestor clip for fill corners.** A composited child (`translate3d`/`will-change`) is clipped badly by an ancestor's `border-radius` + `overflow: hidden` on iOS Safari — the fill's square corners poke past the rounded border. Fill layers inside a bordered, rounded container carry their own concentric radius (`max(0px, calc(var(--radius-card) - 1px))`, one border-width tighter).
- **Media-query branching rule** (below) applies to every family.

### Theme file contract

- `codoxear/static/themes/<family>.css` holds the light palette on `:root[data-theme="<family>"]` and the dark palette on `:root[data-theme="<family>"][data-mode="dark"]`; `paper.css` holds only the dark block because paper light is `app.css` itself. Dark blocks also set `color-scheme: dark` and an inverted `--icon-muted-filter`.
- **Token coverage is tested.** `tests/test_theme_token_coverage.py` requires every color-literal token in `app.css` `:root` (except declared theme invariants such as `--video-bg`) to be overridden in each family's light and dark block. Adding a color token obliges every family file; adding a family obliges a full palette.
- **Component rules mirror base specificity.** Family structural rules are written as `:where(:root[data-theme="<family>"]) <base selector>` so they outrank only the exact base rule they replace (by source order — the theme link follows `app.css`), and more specific base variants (error/warning bubbles, active badges, disabled primaries) keep winning unless the family mirrors them explicitly. A bare `:root[data-theme]` prefix on a component rule is a specificity leak. A rule may add a mode condition inside the `:where()` scope (`[data-mode="dark"]`, `[data-mode="light"]`, `:not([data-mode="dark"])`) — that changes when the rule applies, never its specificity.
- **Cascade order:** `app.css` → `themes/<family>.css` → custom-CSS `<style>` (user CSS, localStorage only, no server endpoint). Theme files are versioned, gzip-compressed, immutable-cached like `app.css`.

### Paper theme

The e-ink language of the base stylesheet: paper light is what `app.css` ships, so every other family starts from its tokens and retunes them; paper dark inverts it (warm near-black paper, light ink rules) as a token block. Paper dark's one mode adaptation: chrome controls and seams drop from full ink to hairline strength, because light-ink perimeters on every button read as glare at night; content containers (cards, bubbles, dialogs, tables) keep the 1px ink signature.

- **Square, warm-charcoal palette.** Geometry stays square (all radius tokens `0`); `--ink` and `--border` are warm charcoal `#2f2b26`, with paper white, `#f6f5f1` background, and `#efeee9` wash.
- **Ink-on-paper primaries.** Primary actions invert warm charcoal and paper. No accent-blue primary.
- **Square state dots.** `--radius-dot: 0`.
- **No decorative shadows.** `--shadow-pop: none`; `box-shadow`/`outline` only for functional focus/state indication. No `backdrop-filter`.
- **Generic sans-serif** (`--font-ui: sans-serif`), prose headings inherit it.

### Clay theme

Warm editorial language: cream paper, terracotta accent (`--accent`, `--on-accent`), radii 6/12/18px, pill badges, circular state dots, soft elevation on floating surfaces. Structural rules: hairline chrome borders, accent-filled primaries and active icon buttons, an accent left rule on the active session, a bordered composer pill. Focus rings are accent-colored. Typeface is paper's (family-invariant); clay's difference is color, geometry, and chrome, never font.

### Slate theme

ChatGPT-like language: white/soft-gray (dark: `#212121`/`#171717`), radii 8/12/18px, pill badges, circular dots, monochrome ink primaries. Structural rules: ghost icon buttons (border only through hover fill), borderless sidebar rows with fill selection, flat assistant messages (user turns keep a filled bubble; error/warning variants keep their borders), a 24px composer pill, hairline dialog borders. Typeface is paper's (family-invariant); slate's difference is color, geometry, and chrome, never font.

### Media-query branching rule

The design constitution restricts new media-query behavior to retuning tokens, visibility, and layout changes. Do not use viewport-specific color, radius, font, or border restyling as a substitute for a component decision. When behavior really differs by viewport, branch the component.

The sanctioned component branches are:

- **Sidebar drawer** — fixed off-canvas on narrow viewports, static column on wide.
- **Session-card reveal mechanism** — touch uses swipe-revealed actions; desktop uses hover-revealed inline actions. This DOM split is **LOCKED**: do not unify the two branches (`useDesktopSessionActions()` / `swipeActions` flag in `app_session_helpers.js`).
- **Viewer fullscreen takeover** — file viewer takes over the viewport on small screens.
- **Hover → always-visible flips** — controls revealed on hover for fine pointers become persistently visible on coarse-pointer/touch.
- **Composer safe-area / anti-zoom** — iOS safe-area insets and input-focus anti-zoom handling.

## Development reminders

- Do not commit secrets: `.env`, `env`, keys, tokens, logs.
- Do not commit runtime artifacts: `codex-homes/`, `socks/`, `root-repo/`, `server.log`, `hmac_secret`, `__pycache__/`.
- Keep shared helpers in `codoxear/util.py` (avoid duplicating log-scan and app-dir logic across modules).
- When a subsystem is semantically wrong, replace it instead of layering more patches onto the broken structure.
- Prefer the smallest invariant-preserving model over incremental adaptation of an already confused implementation.
- Do not let internal pipeline stages redefine user-facing semantics. Define the semantic invariant first, then make the implementation mechanically preserve it.
- For queueing/streaming features, write down the exact replacement/commit boundary first (for example what counts as "queued", what counts as "playing", and what is still replaceable) before writing code.
- If the user provides a simpler design that preserves the invariant more directly, prefer that design over a more elaborate agent-invented state machine.
- For broker/server/session/tmux verification, Docker is the isolation boundary. A host-side throwaway `HOME` only redirects files; it does not isolate the process table, tmux socket, `/tmp`, signals, or systemd. Do not use host throwaway-HOME repros for broker/server/session work.
- Never use pattern-based process cleanup (`pkill -f`, `killall`, broad `pgrep | xargs kill`) in agent-run verification. If a host process is explicitly started for a non-session task, record its exact PID and clean up only that PID; prefer Docker container teardown for anything session-related.
- **Experience the product.** Unit tests and source checks verify structure, not behavior. Before claiming any user-facing feature works, exercise it through the real interface (browser, API, CLI) and observe the actual outcome.
- **Never claim completion without behavioral verification.** "Tests pass" and "code looks right" are not evidence. The evidence is: the user does the thing and the expected result appears.
- **Never swallow a user request.** Every request gets tracked, investigated, and either resolved or explicitly deferred with the user's knowledge. Silence is not a resolution.
- **When the user states a design rule, implement exactly that.** Do not add logic the user didn't ask for. Do not "improve" their rule with additional conditions.
- **When the user reports a bug, investigate their specific case.** "It works for me" is not a valid response. Reproduce their exact scenario. If you can't, say so and ask what they see.
- **Verify the interface before diagnosing the implementation.** Check the exact URL, API key names, parameter names, and response schema against the source before concluding anything is broken.
- **Test in Docker only.** Never probe, test, or verify against the live deployment (127.0.0.1:8743). All behavioral testing uses `scripts/docker_verify.sh` or Docker-isolated agent-browser sessions.
- Local dev:
  - Install: `python3 -m pip install -e .`
  - Run server: `codoxear-server` or `python3 -m codoxear.server`
  - Broker (Codex): `codoxear-broker -- <codex args>`
  - Broker (Pi): `CODEX_WEB_AGENT_BACKEND=pi codoxear-broker -- <pi args>`
  - Broker (Claude Code): `CODEX_WEB_AGENT_BACKEND=cc codoxear-broker -- <claude args>`

## Deployment: committed snapshot only

The deployed server must never import Python or static assets from `/home/yiwen/codoxear`, because concurrent edits in that checkout are development state, not release state. Deploy a reviewed commit with:

```sh
scripts/deploy.sh <commit-ish>
```

The script resolves the commit, creates or updates the detached worktree at `~/.local/share/codoxear/deploy`, verifies it reached that exact commit, runs `pipx install --force` against the snapshot, rewrites only the service's `WorkingDirectory` and `ExecStart`, then reloads and restarts **only** `codoxear-server.service`. It preserves the existing unit's `Environment=` and `EnvironmentFile=` settings, so the password/config remains external to the code snapshot and all runtime data remains under `~/.local/share/codoxear/` (`socks/`, uploads, queues, session stores, and so on).

The script refuses to reinstall or restart when the snapshot path is not this repository's clean worktree or the worktree cannot be updated to the requested commit. The single exemption is the tracked `codoxear/static/dist/app.bundle.js`: every deploy rebuilds it from the reviewed source, so the script restores a stale rebuild left by a previous deploy before the dirtiness guard; all other dirty or untracked paths still block the deploy. Its health boundary is `/` → `200` and unauthenticated `/api/sessions` → `401`.

To roll back, deploy the previous release commit:

```sh
scripts/deploy.sh <previous-commit>
```

That repoints the same snapshot worktree and service at the previous committed code; it does not move or delete live brokers, backend CLIs, sockets, uploads, or session state. Do not restart via process matching or manually point the service back at the editable checkout.

## Ops notes

- Restarting `codoxear.server` does **not** lose session content. Sessions live in backend log files on disk; the server only reads them.
- To avoid losing live sessions, **only** restart the server service. Do **not** kill `codoxear-broker` or the underlying backend CLI process.
- The supported service operation is `systemctl --user restart codoxear-server.service`; deploys must use `scripts/deploy.sh <commit-ish>` above.

## Testing policy (absolute)

- **No source-string tests, ever.** They are worse than nothing: they break on every refactor, produce false confidence without verifying behavior, and cost maintenance on every change. Do not assert on raw file contents (`read_text` + `assertIn`, regex over source, checking that code contains a literal). Tests verify BEHAVIOR: execute the code (VM harnesses for JS, direct calls for Python) and assert outcomes; for CSS, parse the stylesheet and assert computed rules per selector — never substring matching. If a contract has no behavioral check feasible, document it in AGENTS.md instead of a test.
- **Conversation copy contract.** `app_conversation_copy.js` is authoritative for the copyable text and message count. Composition must export the selected session, copy that formatter result, and use its `messageCount` for singular/plural success feedback; it must preserve the formatter's known transcript-export-size message and show generic copy failures otherwise. The composition boundary itself has no stable standalone VM seam, so validate it through the real Copy Conversation UI flow rather than source slicing.
