### Direct session-runtime narrowing

The six direct runtime field APIs currently account for **60 contract-key incidences**:

- `selected`: `getSelected` 19 + `setSelected` 1 = **20**
- `sending`: `getSending` 6 + `setSending` 4 = **10**
- `running`: `getCurrentRunning` 6 + `setCurrentRunning` 4 + `setRunning` 1 = **11**
- `queueLen`: `getQueueLen` 2 + `setQueueLen` 1 = **3**
- `subagentsRunning`: getter 3 + setter 3 = **6**
- `turnOpen`: getter 4 + setter 6 = **10**

This total intentionally counts the explicit state access keys, not the separate `selectedSession` / `selectedSessionId` aliases (**10 additional keys**) nor token, which currently crosses controller boundaries as `setContext` rather than a state accessor.  Phase 3 should replace the **60** field-specific access keys with one injected `sessionState` capability only where a controller must perform state logic, and with subscriptions inside rendering widgets.  The aliases should be collapsed during the same migration, yielding a potential **70** direct selected/runtime accessor-key reduction once file and interrupt routes also use the store.

## Migration order — rank = contract-key reduction × inverse risk

Risk is ranked from the actual coupling observed above: **low** means a value has one producer/one dialog projection; **medium** means refresh/list fanout; **high** means asynchronous selection, stale-result guards, or concurrent SSE/poll reconciliation.  This is a prioritization heuristic, not a success criterion.

| Rank | Cluster / first migration slice | Current explicit contract-key reduction | Risk | Why this ordering is mechanically justified |
|---:|---|---:|---|---|
| 1 | **session-runtime projection** — introduce `app_session_state.js`; migrate `selected`, `running`, `queueLen`, `subagentsRunning`, `turnOpen`, `sending`, then token snapshot | **60 now**; **70** when selected aliases collapse | high | Largest narrowing by far and the only change that structurally removes the duplicated status/queue/context/typing render routes.  Start with a per-field get/set/subscribe API; transition writers before attaching widget subscriptions. |
| 2 | **launch defaults/config** — `newSessionDefaults`, `tmuxAvailable` | **5** direct config keys: `defaultsSource`, `setNewSessionDefaults`, `getNewSessionDefaults`, `tmuxAvailable`, `setTmuxAvailable` | low | Refresh is the sole producer and new-session/composer are bounded consumers.  Keep separate from selected runtime state. |
| 3 | **session-list data** — `latestSessions`, `sessionIndex`, `recentCwds` | **11** direct list-state keys: session-index 7, latest-sessions 2, recent-cwds 2 | medium | One refresh producer already materializes all three; map mutation in send lifecycle and file consumers makes it unsafe to mix with runtime-store migration without first naming list ownership. |
| 4 | **polling** — generation, timers, enabled flags, error streaks | **8** generation keys in wiring (`getPollGeneration` 4 + `getPollGen` 2 + two mutations), plus composition-local timer state | high | Poll generation is a correctness boundary for stale async results; extract after runtime writes are centralized, into the plan’s future `app_polling.js`.  App disposal is app-lifecycle state rather than a polling-store field. |
| 5 | **controller registry** — late-bound controller references | 0 | medium | Not state API; moving it does not shrink contracts.  Retain local construction-order references until composition-residual phase. |
| 6 | **ephemeral UI** — focus/promise/perf state | 0 | low | Local modal and performance state has no cross-controller field contract; do not build a store for it.  Delete only the five demonstrated dead bindings (`pendingHashSessionId`, `pendingHashSessionSelectInFlight`, composition `lastToken`, and the shadowed composition click-metric pair) in a scoped cleanup. |
